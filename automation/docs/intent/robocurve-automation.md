## 목적과 성공 기준

사람의 개입을 최소화하면서 하루에 채택 가능한 수준의 태스크 1개를
아이디에이션부터 제출 직전까지 완성한다. 제출량보다 품질과 전체 흐름의
안정화를 우선한다. 실제 채택 여부는 대회 심사 결과이며, 자체 검증 통과와
구분한다. 하루 목표를 맞추기 위해 품질 기준을 낮추지 않는다.

연구실의 RoboCurve 참가 작업에 사용한다. 기존 파이프라인 코드는 확보하지
못했으므로 새로 구성한다. 기존 과자봉지 실험과 이 프로젝트는 별도로 관리한다.

## 아이디에이션 범위

- 카테고리는 **Impact on AI timelines**에 집중한다.
- 로봇 제작 또는 데이터센터 작업의 자동화에 직접 연결되는 작업을 다룬다.
- 추측이나 사고 실험이 아니라 실제 산업의 작업·장비·절차에 근거해야 한다.
- 로봇 산업·데이터센터 산업·AI 산업에서 로봇으로 자동화할 의미가 있는
  물리 조작이어야 한다. 반드시 극도로 어려운 작업일 필요는 없다.
- 태스크 계획 추론이나 상황 판단 자체보다 실제 물리 조작 능력을 중시한다.
  산업적 의미·신규성과 함께 조작 난도를 평가하고, 가능하면 조작 자체가
  어려운 후보를 우선한다.
  산업적 의미만으로 조작 난도·중요성·차별성 검증을 생략하지 않는다.
  실제 작업의 정렬·접촉·힘 조절·파지 전환·양팔 협응 등에서 어려움이
  발생하는지 설명하고, 문장이나 설정만 복잡하게 만든 난도와 구분한다.
- 상세한 language instruction을 허용한다.
- 외부 참고 자료와 아이디에이션 기준의 세부 구성은 이후 대화에서 확정한다.
- 여러 후보를 검토하되, 제작은 선택한 한 태스크에 집중한다.

## 중복 검사

전 분야의 accept·pending 태스크, 우리 팀의 기존 제출, 기존 벤치마크와
목적·물리 기술·성공 조건을 비교한다. 제목이나 키워드가 다르다는 이유만으로
새로운 아이디어로 간주하지 않는다. 장면 배치, 초기 자세, 물체 형상, 난도,
도구·부품만 바꾼 변형은 충분한 차별성이 아니다.

검사는 반드시 두 번 수행한다.

1. **아이디에이션 시점**: 기존 태스크와 중복되지 않는 후보를 선정한다.
2. **모든 제작이 끝난 제출 직전**: 최신 제출 현황으로 다시 비교하여 제작 중
   발생한 중복을 확인한다.

GitHub PR, 공식 task board, 별도로 동기화하는 DB 중 어떤 수집·비교 방식을
사용할지는 설계 단계에서 결정한다. 비교 자료의 접근 실패나 누락은
중복이 없다는 증거로 취급하지 않는다.

## 에셋과 환경

기존·외부 에셋을 활용해 제작 시간을 절약하되, 재사용을 강제하지 않는다.
필요한 경우 새로 제작하거나 기존 에셋을 수정한다. 실제 작업의 핵심 조작을
유지하고, 에셋의 출처·라이선스·치수·재질·물리 설정을 기록한다.

산업 근거를 조사하는 과정에서 공개 CAD·메시·URDF·USD 등의 에셋도 함께
탐색하고, 사용할 수 있는 자료는 확보해 활용한다. 어떤 실제 장비에 대응하는지,
재사용 조건과 수정 필요 사항이 무엇인지 근거 자료와 연결해 기록한다.
공개 에셋을 찾았다는 것과 필요한 물리 동작이 검증됐다는 것은 구분한다.

실제 로봇 산업이나 데이터센터 산업에서 사용하는 장비의 형태를 재현한다.
라벨만 산업 장비로 붙인 추상 도형으로 핵심 조작을 대체하지 않는다.
기본 제작 범위는 강체 중심이다. 연성체는 필요한 동작이 이미 구현된 기존
에셋·기능을 활용할 수 있고 해당 환경에서 검증할 수 있는 경우에 허용한다.
새로운 연성 물리 모델을 개발하는 작업은 첫 MVP에 포함하지 않는다.

명확한 objective와 성공·실패 조건을 정의한 뒤, 주변 환경·물건·물리 시스템을
갖추고 검증한다. 이후 데모를 실행하며 채점과 기타 문제를 수정한다.
환경 구성과 데모 개발이 서로 불완전한 상태에서 뒤섞여 지연되는 일을 줄인다.
구체적인 환경 완성 판정 조건은 아직 설계해야 한다.

## 데모와 채점

완성된 환경에서 실제 로봇 동작으로 성공 데모를 만들고, 점수와 관측 결과가
일치하는지 검증한다. 최종 위치뿐 아니라 과제의 의미에 중요한 파손·유출·금지
행동도 반영한다. 목표를 달성하는 과정에서 중요한 물체를 훼손해도 성공으로
처리되는 편법을 막는다. 성공시키기 위한 채점 기준 완화는 하지 않는다.

## Dream 평가와 비용

- GPU 환경은 NVIDIA Brev를 사용한다.
- 현재 전체 비용에 별도 상한을 두지는 않는다.
- Dream 비용은 **전체 누적 20달러** 상한으로 관리한다.
- 개발·디버깅 중 반복 호출하지 않는다.
- 환경·데모·채점 구성이 모두 완성된 후 **태스크당 최종 평가 실행 1회**만 한다.
- 그 실행 안에서 필요한 여러 API 요청은 허용한다.
- 평가 결과가 실패해도 자동으로 재평가하지 않는다.

## 사람의 개입과 제출

아이디어 선택부터 검증 및 제출 직전 보고까지 자동으로 진행한다.
사용자가 결과 보고를 검토하고 승인한 뒤 실제 제출한다.
예산 초과·반복 실패 등의 예외 상황에도 사람이 개입한다.
승인 없이 자동 제출하는 방식은 범위에 포함하지 않는다.

## 실행 진입점·GPU 생명주기·결과 보존

CLI를 실제 실행 기준으로 만들고 로컬 전용 skill로 감싼다. 작업 시작은 지정한
Brev 인스턴스 start부터 진행한다. 최종 검토 자료와 복구 기록을 보존한 뒤
검토 대기 시 해당 instance를 stop한다. 승인 후 제출은 GPU 없이 가능한 로컬
경로를 우선하고, 수정 요청 시 instance를 다시 start해 같은 작업을 이어간다.
생명주기 관리와 관련 CLI는 첫 MVP 범위에 포함한다.

작업 결과는 instance 안에만 두지 않는다. benchmark fork에 태스크별 새 작업
브랜치를 만들고 origin에 commit/push해 보존한다. 수정은 같은 브랜치에서
이어간다. 이 보존용 push와 승인 후 대회 PR 제출은 구분한다. 큰 자료는
업로드 전에 크기·보관 방식을 알린다. 상세 명령은
[CLI·skill·생명주기 설계](../design/cli-skill-and-lifecycle.md)를 따른다.

## 아직 결정하지 않은 사항

- 운영 방식, MVP 범위, 단계별 산출물과 통과 조건.
- 아이디에이션 참고 자료와 실제 작업 방식의 근거 수집 방법.
- 중복 비교 자료의 수집·동기화·비교 방법.
- 환경 완성 판정과 데모·채점 수정의 경계.
- 반복 실패의 판정과 수리·보류·후보 전환 규칙.
- 사용자 보고·승인 인터페이스와 승인 후 제출 과정.
- 코딩 에이전트와 Brev 실행 환경의 구체적인 구성.
