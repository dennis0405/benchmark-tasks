# 상세 기술 설계 초안: 산업 근거·에셋·제출 동기화·중복 검사

상태: 구현 전 검토 초안. 작성일: 2026-11-13 (Asia/Seoul).
상위 문서: [기술 구성](technical-architecture.md), [운영 설계](mvp-workflow.md).
표의 데이터 이름·주기·검색 개수는 설계 제안이며 실제 파일·DB·스케줄은 만들지 않았다.

## 1. 데이터의 흐름과 저장

```text
산업 원문 ── 수집·추출 ── 근거 카드 ──┐
공개 에셋 ── 확보·검사 ── 에셋 카드 ──┤→ 후보 생성 → 산업적 의미·물리 난도·제작 가능성 검토
                                      │                    ↓
GitHub + board + 벤치마크 ── 카탈로그 ─┴────────── 신규성 검사 → 단일 제작 후보
```

MVP 저장은 SQLite 메타데이터와 해시 기반 원본 파일로 구성한다. DB에 큰 PDF·
에셋·영상을 직접 넣지 않는다. 원본, 추출문, 에이전트의 해석, 채택된 판단을
구분한다. 원본을 확보할 수 없으면 `reference-only` 상태와 접근 가능한 증거를
기록한다. 전체를 읽었다고 주장하지 않는다.

| 기록 | 주요 필드·관계 |
|---|---|
| SourceRecord | source_id, URL, 발행 주체, 제목/버전, 조회 시각, 원본 해시, 확보 상태, local object reference |
| EvidenceCard | claim_id, 주장, 직접 관측/원문 사실/추론 구분, source_id, 페이지·절·시간·이미지 위치, 원문 인용, 미확인 사항 |
| AssetRecord | asset_id, 대응 장비·부품, 출처, 라이선스 원문 참조, 파일 해시·형식·단위·치수·관절/충돌 정보, 수정 이력, 검증 상태 |
| TaskRecord | 내부 ID, 외부 task ID/PR/benchmark ID, 출처별 상태, origin/revision, instruction/setup/scoring, 이미지·코드 참조 |
| TaskSignature | 목적·장비/물체 종류·setting·핵심 물리 기술·성공 조건·중요 제약, 원문 hash, 추출기 버전, 불확실성 |
| CandidateCard | 산업 근거, 자동화 가치, 조작 난도, 장비·에셋 계획, 측정 방법, 제작 가능성, 연결된 claim/asset ID |
| SyncRun | 범위, 시작/종료, 페이지 처리 이력, 수집·실패·누락 수, watermark, snapshot ID, completeness |
| NoveltyReport | 후보·카탈로그 버전, 전수 요약 대조 범위, 상세 비교 ID, 차이/겹침 근거, 판정·반박·불확실성 |

각 판단에는 입력 원문과 프롬프트/모델 버전을 기록한다. 원문이 바뀌면 해석과
검색 임베딩을 갱신 대상으로 표시한다. 동기화는 관측한 사실을 덮어쓰지 않고
이력을 남겨, 과거 보고서가 어떤 제출 상태와 자료를 기준으로 했는지 재현한다.

## 2. 산업 자료 수집

### 역할 분리

1. **research-planner**: 로봇 조립·설치·정비 또는 데이터센터 작업의 조사 가설,
   장비명, 실제 작업 용어와 검색 질의를 작성한다. 검색 범위·추가 근거가 필요한
   주장을 지정한다. 처음부터 그럴듯한 새 task를 발명해 근거를 끼워 맞추지 않는다.
2. **collector 도구**: Search API로 원문을 찾고 HTTP/PDF/브라우저 어댑터로 확보한다.
   검색 결과와 원문은 별개다. 중복 URL·동일 해시를 연결하고 불필요한 재수집을 줄인다.
3. **evidence-analyst**: 원문을 작업 단위로 정리하고 주장마다 페이지·절·시간 위치를
   붙인다. 실제 절차, 장비의 역할, 산업적 자동화 가치, 조작 자체의 어려움을 추출한다.
4. **validator 도구**: 필수 필드, source ID, 인용 위치·텍스트, 확보 상태를 확인한다.
   OCR/표/도면의 부정확한 추출을 정상 원문으로 확정하지 않는다.

### 소스 우선순위

제조사 설치·서비스 매뉴얼, 공식 조립 절차, 공개 산업 설계와 실제 작업 영상·
보고서를 우선한다. 검색 결과의 마케팅 문구만으로 작업의 존재·빈도·자동화
효과를 확정하지 않는다. 수치가 없으면 임의의 절감 시간이나 위험도를 생성하지 않는다.
구체적인 제조사·단체·자료 목록은 아직 미확정이며 사용자와 별도 검토한다.

문서는 원문과 PDF 페이지별 텍스트를 보존하고 필요한 도면·표·이미지를 함께
확인한다. 영상은 제공된 자막과 시간 위치를 사용하며, 조작의 접촉·체결이
핵심이라면 해당 구간 프레임도 확인한다. 원문 접근 실패는 재시도/다른 원문
탐색으로 처리하고, 모델의 기억으로 빈칸을 채우지 않는다.

### 조사 완료 조건

후보의 작업 목적·정상 절차·장비 역할·자동화 가치가 근거로 연결되고, 사실과
추론을 구별할 수 있어야 한다. 조작 난도도 실제 공차·힘 조절·접촉·협응 등의
요구로 설명한다. 어려운 조작이 없더라도 검토는 가능하지만 비슷한 후보 사이에서
의미 있는 조작 능력을 요구하는 쪽을 우선한다. 설명 난도를 물리 난도로 세지 않는다.

## 3. 공개 에셋의 탐색·확보·검사

산업 자료 조사와 동시에 장비 모델명/부품번호/도구명으로 공개 CAD·mesh·URDF·
USD를 찾는다. 제조사 원본이나 해당 에셋의 공식 배포처를 우선 확인하되, 외부
저장소도 출처와 활용 조건을 확인해 사용할 수 있다. 아직 특정 에셋 저장소를
필수 의존성으로 정하지 않는다.

| 절차 | 도구·처리 | 상태/산출물 |
|---|---|---|
| 발견 | 웹 검색·제조사 링크·GitHub API | `discovered`, 대응 장비와 원문 위치 |
| 출처·활용 조건 확인 | 라이선스 파일·배포 페이지 확보, asset-analyst 해석과 원문 연결 | `reference-only / acquisition-ready / permission-unclear` |
| 원본 확보 | 다운로드 도구·크기/형식 확인·SHA-256·참조 파일 목록 | `acquired`, 원본과 manifest |
| 정적 검사 | XML/mesh/USD 등 형식별 parser, 단위·bounding box·관절·충돌 참조 확인 | `inspected`, 검사 결과와 누락 |
| 적합성 평가 | 도면/사진·명세와 형상·치수 대조, 수정·변환·관절 추가 필요성 판단 | `usable-as-input / adaptation-needed / unsuitable` |
| 환경 반입 | 후속 환경 역할에서 변환·수정·물리 시험 | `runtime-validated`, 검증한 환경·버전·시험 기록 |

`usable-as-input`은 바로 쓸 수 있는 시뮬레이션 에셋이라는 뜻이 아니다. 특히 STEP
파일은 CAD 변환이, 시각용 mesh는 충돌/관절 설정이 필요할 수 있다. 변환 도구와
수치 오차는 환경 기술 설계에서 정하고 실제 장비의 핵심 형상을 유지하는지 검사한다.
에셋이 없으면 직접 제작하는 경로를 남긴다. 원본과 수정본·변환본은 각각 해시와
출처를 연결한다. 검사 과정에서 배포물의 임의 설치 스크립트를 실행하지 않는다.

연성 에셋은 형상만이 아니라 필요한 변형·접촉 기능, solver/버전, 실행 예제와
검증 결과까지 확인한다. 새 물성/solver 연구가 필요하면 첫 MVP에서는 보류한다.

## 4. 기존 제출 카탈로그: 수집 출처와 권위

### 두 소스를 결합

- **GitHub**: PR 목록·본문·라벨·댓글·revision과 코드/manifest를 확보하는 주 수집원.
  데이터 수집과 재시도는 프로그램이 담당하고 LLM이 페이지 순회를 지휘하지 않는다.
- **공식 board**: task ID·심사 상태·제출/수정 정보·공개 자료를 대조한다. 문서화된
  수집 API가 있는지는 아직 확인하지 못했다. 없다면 로그인된 Playwright의 실제
  UI·페이지네이션으로 읽는다. 숨겨진 엔드포인트를 추측해 필수 의존성으로 만들지 않는다.

GitHub `open`을 `pending`, `closed`를 `rejected`로 바꾸지 않는다. merged 여부,
공식 접수·심사 댓글, board 상태와 각 관측 시각을 저장한다. 출처가 충돌하거나
등록만 된 PR이 실제 접수됐는지 불명확하면 `unknown/conflict`로 남긴다.
단순히 마지막으로 읽은 값을 진실로 덮어쓰지 않는다.

자기 팀 여부는 author 이름만으로 추측하지 않는다. board 팀 연결·등록된 제출자
설정에 근거한다. 내부 비교용 식별 정보는 블라인드 제출물에 노출하지 않는다.

### 최초 동기화

1. `/repos/robocurve/benchmark-tasks/pulls?state=all&sort=created&direction=asc&per_page=100`
   목록을 `Link` 페이지네이션 끝까지 읽는다. GitHub 검색은 수집원이 아닌 보조 조회다.
2. PR 상세와 issue comments를 읽어 접수 task ID·심사·수정 이력을 보존한다.
   공식 작성자/봇과 board 대응을 확인한다. 댓글 형식은 버전 있는 parser로 읽고
   해석 불가 문구는 원문과 `unknown`을 남긴다. 임의 댓글의 접수 주장을 신뢰하지 않는다.
3. head SHA/수정 버전에 고정해 파일 목록과 `task.json`·README·핵심 소스를 확보한다.
   fork PR은 head repository와 SHA를 함께 기록해 해당 출처에서 확보한다.
   fork 삭제 등으로 확보할 수 없으면 대체 archive의 동일 revision 여부를 확인하고,
   확인 불가 상태를 기록한다. 현재 main으로 pending·과거 제출본을 대신하지 않는다.
4. board의 모든 필요한 상태/페이지를 읽고 외부 task ID·PR 관계를 맞춘다.
   하나의 PR에 여러 접수/수정 ID가 있을 수 있으므로 일대일로 가정하지 않는다.
5. 출처별 총량, 처리 페이지, 실패·미매핑·필수 정보 누락을 기록한다. 필요한 범위가
   완성되기 전에는 그 sync snapshot을 신규성 검사에 사용할 `complete`로 승격하지 않는다.

GitHub PR 파일 API는 3,000파일 제한이 있으므로 파일 수·누락 여부를 점검한다.
manifest가 여러 개이거나 제출 snapshot과 현재 head의 대응이 불명확하면 보류한다.
대기 중 push가 심사에 반영된다고 가정하지 않는다. 심사 대상 버전을 특정할 수
없으면 관련 revision들을 비교 대상으로 유지하고 불확실성을 보고한다.

### 증분 동기화

- PR 목록은 `sort=updated&direction=desc`로 읽고 이전 성공 watermark보다 이전
  구간까지 여유 범위를 두어 처리한다. PR 목록 endpoint에 없는 `since`를 가정하지 않는다.
- 댓글은 repository issue comments의 `since` 지원을 활용하되 반환 순서·페이지를
  실제 API 계약대로 처리한다. 댓글과 PR 정보는 독립적으로 갱신한다.
- 주기적으로 전체 목록을 재조정하고 open·최근 수정/반려 대상과 board를 대조한다.
  댓글 삭제·라벨 수정·board만의 변경은 단일 watermark만으로 완벽히 추적되지 않는다.
- 모든 페이지·필수 상세가 성공한 뒤 DB transaction으로 새 snapshot과 watermark를
  확정한다. 중간 실패는 이전 성공 snapshot을 남기고 `incomplete` 실행 기록을 추가한다.
- 페이지를 읽는 중 목록이 변할 수 있다. 시작·종료 시각과 겹침 구간·재조정 결과를
  기록한다. API의 단일 시점 snapshot인 것처럼 표현하지 않는다.
- 호출은 큐에서 직렬 처리하고 ETag/조건부 요청, retry-after·rate-limit reset을 따른다.
  401/403을 빈 목록으로, 404를 일괄 삭제 신호로 처리하지 않는다.

**주기 제안, 미확정:** 시작 시/아이디에이션 전/제출 직전 동기화는 필수.
제작 중에는 30분 간격의 가벼운 증분 갱신, 하루 1회 목록 전체 재조정을 우선
검토한다. 실제 갱신량·rate limit·board 수집 비용을 보고 조정한다. 웹훅이 가능한
권한과 운영 환경이 있으면 후속 개선으로 검토하되 MVP에 공개 수신 서버를 요구하지 않는다.

### 비교 범위와 completeness

전 분야 accepted·pending, 자기 팀의 과거 제출, 공식 규칙상 보호되는 반려/수정
태스크를 기록한다. 상태 불명인 open PR도 사라진 것으로 보지 않고 비교 대상으로
보수적으로 유지한다. 알려진 벤치마크는 별도 importer로 suite·버전·원문 task ID를
보존하고 고정 목록을 관리한다. 벤치마크 목록 자체는 후속 확정한다.

`complete`는 **선언한 소스 범위의 수집 완성**을 뜻한다. 세상 모든 벤치마크를
다 읽었다는 뜻이 아니다. 필요한 active task의 setup/scoring이 빠졌거나 board
범위를 확인하지 못했다면 최종 중복 검사는 보류한다. 과거의 무관한 PR 한 건이
깨졌다는 이유로 무조건 전체 중단하지는 않되 제외 이유·영향을 기록해야 한다.

## 5. 중복 검사: 전수 요약 대조 + 혼합 검색 + 원문 판정

### TaskSignature 정규화

task-normalizer는 instruction만 요약하지 않고 setup·scoring·관련 이미지를 함께
읽는다. 원문 표현은 보존하고 검색용 영어 정규화 표현·동의어를 보조 필드로 둔다.
객체 이름이 아닌 종류, 장비의 실제 setting, 핵심 조작, 목표 상태와 실패 조건을
명시한다. 원문에서 확인되지 않는 난도나 체결 원리는 만들어 넣지 않는다.

분류는 정렬, 삽입, 체결, 분리, 라우팅, 접촉 유지, 힘 조절, 파지 전환, 양팔 협응
등의 열린 어휘를 사용하되 고정 분류 하나로 비교 대상 전체를 잘라내지 않는다.
카테고리가 다른 task도 동일 조작을 평가할 수 있으므로 분야 필터로 제외하지 않는다.

### 대조 과정

1. **전수 요약 대조**: 후보의 서명과 카탈로그 전체 서명을 batch로 비교한다.
   각 기록을 `겹침 가능 / 명백한 다른 목표·조작 / 정보 부족`으로 분류하고 근거를
   남긴다. 생략한 batch·토큰 잘림·추출 실패는 미검토로 표시한다.
2. **혼합 검색**: 전체 자료에 FTS5 BM25, BGE-M3 dense cosine 검색, 조작·목적·
   성공 조건·장비 동의어별 확장 검색을 적용한다. 원문 요약과 구조화 필드를
   별도 검색해 특정 표현에만 의존하지 않는다.
3. **상세 비교 대상 합집합**: 전수 대조의 가능/정보 부족, 검색에서 가까운 결과,
   자기 팀의 같은 계열, 명시적으로 연결된 revision을 포함한다. 상위 검색 개수만
   남기고 명시적 의심 사례를 버리지 않는다.
4. **원문 비교**: novelty-reviewer가 목적·물체 종류/setting·핵심 물리 능력·
   성공 조건을 축별로 대조하고, 같음/다름/불명과 source reference를 기록한다.
   의심 결과는 원문·이미지·코드의 필요한 부분을 추가 확보한다.
5. **반박 검토**: novelty-critic이 빠진 유사 계열과 표면적 차이만으로 통과시킨
   근거를 찾는다. 두 역할이 실질적으로 충돌하면 자동 통과시키지 않는다.
6. **보고/선정**: `중복 / 차별성 근거 있음 / 불확실`로 판정한다. 중복은 후보 제외,
   불확실은 근거 추가 확보/예외 검토, 차별성 근거가 있는 후보만 다음 평가로 넘긴다.

**검색 기본값 제안:** FTS 30건·dense 30건에서 시작하되 이 수치들은 정답/중복
판정 임계값이 아니다. 전체 요약 대조의 의심 사례와 다른 검색 결과를 합쳐
상세 검토 대상을 늘린다. 단일 cosine 점수나 자동 계산한 신규성 점수로 통과시키지 않는다.
카탈로그 규모가 커지면 비용·지연을 측정해 batch와 캐시를 조정하고, 전수 범위를
줄일 경우 품질 영향과 사용자 결정을 거친다.

### 캐시와 결과 무효화

정규화·임베딩 캐시 키는 원문 해시 + parser/normalizer/model revision이다.
후보의 objective·형상·조작·성공 조건이 바뀌면 후보 서명과 비교 보고서를 갱신한다.
기존 task의 변경은 해당 서명·검색 인덱스만 갱신하되 중복 판정 영향은 재평가한다.
모델 변경 시 다른 임베딩 공간의 벡터를 섞지 않는다.

최종 검사에는 완성된 실제 명세·setup·scoring과 최신 snapshot을 사용한다.
선정 당시 계획과 실제 구현이 달라졌는데 옛 후보 카드로 비교하지 않는다.
승인 대기 중 새 유사 task가 생기면 보고·승인을 낡은 상태로 표시한다. 비교 대상이
나중에 생긴 것인지, 더 이른 origin을 가진 수정본인지 공식 규칙에 맞춰 구분한다.

## 6. 초기 검증 설계

구현 후 다음 사례를 검증한다. 아직 실제 테스트나 정확도 측정을 수행하지 않았다.

- 같은 조작을 다른 제목·언어·부품명으로 적은 양성 중복.
- 같은 장비라도 목표·핵심 물리 능력이 다른 구별 사례.
- 물체·난도·배치만 바꾼 변형과 단순 단계 추가.
- 서로 다른 카테고리에 있는 동일 능력, 자기 팀의 기존 계열.
- 자료 누락, 해석 불가 댓글, board/GitHub 충돌, 잘린 pagination, 중간 429·인증 만료.
- 제작 중 새로 접수된 task, pending revision, 심사 대상 SHA와 현재 head가 다른 경우.
- 검색 상위권 밖의 중복이 전수 대조/확장 검색에서 발견되는지 확인.

과거 심사 피드백에서 뽑은 평가 쌍을 근거와 함께 만들되, 일부는 검색·판정
설정 조정에 쓰지 않은 holdout으로 남긴다. 작은 라벨 집합의 높은 정확도를
전체 무중복 보증으로 해석하지 않는다. 중복 누락과 과도한 보류를 별도로 측정한다.
