# MVP 운영 설계: 산업 근거에서 승인 후 제출까지

상태: **설계 검토 초안**. 확정된 범위는 [제작 의도](../intent/robocurve-automation.md)에
기록했다. 이 문서의 상세 통과 조건과 기본값 제안은 아직 사용자가 검토하지 않았다.
기준일: 2026-11-13 (Asia/Seoul). 코드·배포·실험·제출을 실행한 문서가 아니다.

## 1. 범위와 판정 원칙

- 사용자 확정: 산업 근거 기반 후보 다수 검토, 제작은 한 태스크에 집중,
  AI timelines 분야, 장비 형태 재현, 강체 우선, 기존 연성 에셋은 검증 후 허용.
- 자체 품질 검사 통과, 사용자 승인, 외부 접수, 대회 채택을 서로 다른 상태로 기록한다.
- 산업적 중요성과 물리 난도를 혼동하지 않는다. 자동화의 반복성·인력 부담·작업
  시간·가동 중단·제조/정비 병목 등을 근거로 설명할 수 있다. 정량 수치가 없다면
  발명하지 않고, 정성 근거와 그 한계를 명시한다.
- 중요한 작업이라고 해서 기존 벤치마크의 동일 조작을 새 태스크로 제출하지 않는다.
- 산업적 의미·신규성·조작 난도를 각각 평가한다. 필수 조건을 만족하는 후보 중
  가능하면 물리 조작 자체가 더 어려운 후보를 우선한다. 단순한 추론이나 단계
  나열로 만든 난도는 대체물이 아니다. 조작 난도가 높다는 이유로 산업 근거,
  신규성 또는 재현 가능성의 결함을 상쇄하지 않는다.
- 모델이 판단한 성공보다 기록된 물리 상태와 재현 가능한 검사 결과를 우선한다.
- 자료가 없거나 검사기가 실패하면 통과로 간주하지 않는다. 불확실성과 실패를 구분한다.
- 완료를 위해 objective·실패 조건을 약화하거나 Dream 시도 기록을 초기화하지 않는다.

## 2. 기능 경계 제안

다음은 검토할 기능 구분이다. 에이전트·도구·데이터 계약은
[기술 구성 초안](technical-architecture.md), [자료·신규성 검사](sources-and-novelty.md),
[환경·물리 검증](environment-and-validation.md),
[데모·채점·평가·제출](demo-evaluation-and-submission.md)에 구체화했다.
구현 순서와 실제 에이전트 배치는 아직 확정하지 않는다.

같은 태스크의 재개와 외부 심사 후 수정은 새 후보 생성과 구분한다.

## 3. 단계별 산출물·통과 조건·실패 처리

아래 파일 이름은 산출물의 예시이며, 파일·DB 형식은 기술 설계에서 결정한다.

| 단계 | 필수 산출물 | 통과 조건 | 실패·불확실 시 처리 |
|---|---|---|---|
| 0. 사전 점검 | 공식 규칙·심사 프롬프트 버전, 환경·계정·기존 실행 상태, 외부 자료 수집 상태 | 필요한 접근·실행 기능이 확인되고 진행 중인 작업과 충돌하지 않음 | 접근·환경 문제를 해결하거나 대기. 외부 상태를 추측해 진행하지 않음 |
| 1. 산업 근거 조사 | 원문 출처, 작업·장비·절차·자동화 가치의 근거, 관련 공개 에셋 후보와 확보 자료 | 자료가 해당 작업의 존재와 방식, 로봇 제작/데이터센터와의 직접 연관성을 뒷받침. 에셋의 대응 장비·출처·활용 조건을 확인 | 근거 부족은 조사로 반환. 에셋이 없으면 제작 가능성을 별도 검토하며 중요성을 꾸며 후보화하지 않음 |
| 2. 후보 생성·선별 | 여러 후보의 objective·물리 기술·성공 조건, 산업적 의미·신규성·조작 난도 비교표, 선정/탈락 이유 | 근거·중요성·신규성·장비 재현·채점 가능성을 만족하고 가능하면 조작 자체가 어려운 후보 1개 | 중복 후보 제외. 난도가 판단 문제나 단계 나열에만 의존하면 재검토. 전부 탈락하면 조사 단계로 반환 |
| 3. 태스크 계약 | 지시문, 실제 작업 setup, 성공/부분 성공/실패, 측정 계획, 필요 상호작용, 근사 허용 범위 | 현실의 성공과 시뮬레이션에서 측정할 성공을 대응시키고 편법·파손 조건을 설명 | 관측할 수 없으면 환경 설계 재검토. 핵심 능력을 제거해야 한다면 후보 보류 |
| 4. 환경 제작·검증 | 장비·도구 에셋, 치수·재질·관절·접촉 설정, 라이선스, 구성요소 시험, reset·관측·카메라 점검 | 장비 형상과 핵심 상호작용을 검증하고 필요한 실패를 관측할 수 있음 | 환경을 수리. 새 연성 물리 연구가 필요하면 MVP 후보에서 보류 |
| 5. 데모·채점 검증 | 로봇 동작 기록·영상, 상태 궤적·점수, 정상/실패 대조군, 깨끗한 reset 재현 | 물리 동작으로 full score, 필수 실패 시 감점/무효, 영상·기록·문서 일치 | 제어 실패는 제어 수정. 물리 문제는 4단계, 명세 문제는 3단계로 반환 |
| 6. 최종 검증·동결 | 자체 심사 보고, 공개 제출 자료, 소스·에셋·설정 해시, 데모 재현 결과 | 중요성·신규성·타당성·재현·채점·실현 가능성의 미해결 핵심 문제가 없음 | 관련 단계로 반환. 검증 통과 전 Dream 실행 금지 |
| 7. Dream 최종 평가 | 한 평가 실행의 영상·궤적·점수·요청 이력·사용액·종료 이유 | 동결된 환경에서 실제 실행 결과가 기록됨. full score는 통과 필수가 아님 | 성능 실패는 그대로 보고. 실행/계측 오류나 상태 불명은 예외 처리, 자동 재평가 금지 |
| 8. 최신 중복 검사·보고 | 최신 비교 자료의 시각·커버리지, 가장 가까운 태스크와 차이, 사용자 검토 보고서 | 제작 중 새로 생긴 중복·우선권 문제를 다시 확인하고 제출 자료에 미해결 핵심 문제가 없음 | 중복 확인 시 제출 차단, 결과 보존. 비교 자료 불완전·중복 여부 불명은 보류 |
| 9. 사용자 승인 | 특정 제출 결과물 버전에 대한 승인 기록 | 사용자가 영상·명세·실제 점수·한계와 중복 검사 결과를 보고 해당 버전을 승인 | 수정 요청 시 관련 단계로 반환. 미승인은 승인 대기로 유지 |
| 10. 제출·접수 확인 | 업로드 결과·미디어 ID, 제출 커밋, PR URL, 접수 응답·태스크 ID | 승인한 내용과 일치하는 자료를 제출하고 외부 접수 여부를 확인 | 접수 실패는 원인별 수정/대기. 응답 불명은 조회 후 판단, PR·업로드를 무작정 재생성하지 않음 |

제작 중 변화가 크면 필수 두 번 외에도 중복을 재확인할 수 있다. 최종 비교 뒤 승인
대기가 길어지거나 새로운 제출이 발견되면 제출 실행 직전에 다시 갱신한다.
원격 요청 사이의 경쟁 상황까지 원천적으로 제거할 수는 없으므로 조회·제출 시각과
근거를 보존한다. 자체 검사는 중복이 절대 없다는 보증이 아니다.

## 4. 산업 근거 계약

### 후보별 기록

- 출처 URL/문서 ID, 발행 주체, 제목·버전·조회일, 관련 페이지/절/이미지 위치.
- 실제 장비·부품명, 해당 산업에서의 작업 목적과 정상 절차.
- 원문이 직접 뒷받침하는 사실, 자동화 가치를 추론한 부분, 아직 모르는 부분.
- 원문 절차에서 태스크 objective로 옮기는 과정과 생략·근사하는 부분.
- 로봇이 조작할 물체, 필요한 접촉·정렬·힘·운동, 실제 완료 판정 방법.
- 수행 방법을 모두 알려준 뒤에도 남는 조작의 어려움과 그 원인. 실제 공차,
  접촉 유지, 체결, 제한된 접근 공간, 힘 조절, 파지 전환, 양팔 협응 등의
  요구가 있다면 원문·장비 형상·실험 결과 중 어떤 근거가 있는지 기록한다.
- 장비 형상·공차·물성·도구의 근거와 에셋으로 옮길 수 있는 정보.

조작 난도는 단일 자동 점수만으로 확정하지 않는다. 비교적 쉬운 작업도 산업적
자동화 가치가 뚜렷하면 검토하되, 조건이 비슷한 후보 사이에서는 더 의미 있는
조작 능력을 요구하는 쪽을 우선한다. 난도를 높이려고 실제에 없는 좁은 공차나
과도한 힘·불리한 배치를 추가하지 않는다. 이 우선순위는 프로젝트의 선정
원칙이며, 공식 심사에 별도의 난도 점수 항목이 있다는 주장과 구분한다.

### 자료 선택 원칙

제조사 설치·서비스 매뉴얼, 공식 조립/정비 절차, 공개 산업 설계 자료, 실제
작업을 확인할 수 있는 영상·보고서 등을 우선 검토하는 방향을 제안한다.
정확한 출처 목록은 사용자와 후속 확정한다. 검색 요약문이나 모델의 상식만으로
근거를 대신하지 않는다. 원문 링크만 수집하고 주장과 연결하지 않은 자료도 부족하다.

자료 수에 대한 일률적인 최소값 대신 주장별 근거를 확인한다. 한 문서가 모든
필수 주장을 직접 뒷받침할 수도 있고 여러 자료가 필요할 수도 있다. 설비·절차가
서로 다른 문서의 유리한 부분을 합쳐 실제로 존재하지 않는 작업을 만들지 않는다.

### 공개 에셋의 동시 발굴·확보

근거 조사 중 제조사 CAD, 공개 설계 파일, 메시, URDF, USD 등 관련 에셋도 함께
찾고, 활용 조건에 맞게 원본을 확보해 재사용한다. 조사 단계의 에셋 후보·확보
상태와 환경 단계의 실제 채택·수정·검증 상태를 구분한다.

- 실제 장비·부품과 에셋의 대응 관계, 원문·다운로드 URL, 배포자, 버전/조회일.
- 라이선스·수정/재배포 조건, 함께 보존할 출처·라이선스 파일.
- 형식·단위·스케일, 치수와 부품 구성, 관절·충돌 형상·물리 재질의 포함 여부.
- 원본과 수정본의 구분, 부족한 기능, 필요한 수정과 환경 시험.
- 연성체는 외형 메시뿐인지, 필요한 변형·접촉 기능과 호환 환경까지 제공되는지.

원본의 장비 형태가 맞아도 바로 시뮬레이션에 쓸 수 있다고 판단하지 않는다.
활용 조건이 불명확하면 해당 에셋의 사용을 보류하고 다른 에셋 또는 직접 제작을
검토한다. 에셋이 없어도 후보를 자동 탈락시키지는 않으며, 새 에셋 제작이 MVP
범위와 작업 시간 안에서 가능한지 평가한다. 특정 에셋 보유 여부 때문에
산업적 목적이나 조작 능력을 바꾸어 후보를 정당화하지 않는다.

### 후보 제외 또는 보류

산업 장비라고 이름만 바꾼 일상 작업, 실제 작업자가 쓰지 않는 임시방편,
역할이 없는 물체를 추가해 만든 난도, 실제 치수/힘을 바꿔야만 가능한 축소판,
핵심 조작의 측정 방법이 없는 태스크는 제외하거나 추가 조사로 돌린다.

## 5. 중복 검사 계약

목적, 물체 종류와 실제 setting, 핵심 물리 조작, 성공 조건으로 후보를 표현한다.
비교는 모든 분야의 accepted·pending, 우리 팀의 기존 제출, 알려진 벤치마크를
대상으로 한다. 현재 공식 규칙상 우선권이 유지되는 반려·수정 태스크도 기록한다.

수집한 PR과 공식 board의 task ID·심사 상태를 연결한다. GitHub의 open/closed만으로
pending/accepted를 단정하지 않는다. 카탈로그는 단순 제목 목록보다 instruction,
setup, scoring, 가능하면 영상/스크린샷과 관련 코드를 포함해야 한다.

어휘·의미 검색은 비교 대상을 찾는 수단이다. 가까운 후보를 고른 뒤 실제 조작과
결과를 비교한다. 전체 기록을 수집했다는 것과 의미 비교가 완벽하다는 것은 다르다.
참고한 자료 범위, 누락, 가장 가까운 태스크와 차이, 미해결 우려를 함께 남긴다.

판정은 `차별성 근거 있음 / 중복 / 불확실`로 나눈다. 불확실은 통과가 아니다.
검색 결과 0건이나 API 실패도 차별성 근거가 아니다. 자체 신규성 점수가 높다는
이유만으로 나머지 필수 조건을 상쇄하지 않는다.

## 6. 환경 준비 판정

다음을 **모두** 검토한 뒤 전체 태스크 데모 개발에 진입한다.

1. **장비 형태**: 원문 도면·사진과 렌더를 대조하고 그리퍼 접근에 필요한 형상,
   잠금부·손잡이·커넥터·체결면 등이 실제 조작을 유지하는지 확인한다.
2. **치수와 배치**: 실제 크기·도구·작업 공간을 명세와 맞춘다. 크기만 임의로
   축소해 YAM이 닿도록 만들지 않는다.
3. **물리 기능**: 필요한 관절, 중력, 마찰, 스프링, 충돌, 맞물림, 유격 등을
   구성요소 시험으로 확인한다. 모든 물성을 재현하려 하지 않고 핵심 기능과
   결과에 영향을 주는 가정·근사를 명시한다.
4. **초기 상태**: reset 후 중첩·낙하·자발적 성공·발산 없이 시작 상태가 재현된다.
   안정화 시간과 허용 오차는 task별로 명시한다.
5. **측정 가능성**: 성공과 중요한 실패에 필요한 관측이 유효하고 갱신되는지
   확인한다. 오래된 상태·누락된 센서값을 정상으로 처리하지 않는다.
6. **로봇·카메라**: 그리퍼 크기, 도달 가능성, 충돌 형상, 제어 주기와 영상 출력이
   해당 작업을 지원한다. 개별 제어·접촉 시험은 환경 검증에 포함한다.
7. **에셋 재현성**: 파일과 참조가 모두 존재하고 출처·라이선스·단위·크기·질량이
   문서와 일치한다. 서버 절대 경로 없이 필요한 자료를 묶을 수 있다.
8. **연성체 예외**: 단순히 mesh가 있다는 것만으로 허용하지 않는다. 필요한 변형·
   접촉 동작이 선택한 런타임에서 재현돼야 한다. 별도 solver·새 물성 연구가
   필요하면 보류한다. 강체 task에도 케이블 등 숨은 연성 의존성이 없는지 본다.

이 단계에서는 reset·낙하·관절·접촉·도달·관측 시험을 한다. full-score 로봇
데모는 다음 단계에서 만든다. 환경 완성은 물리 엔진의 완전한 현실 일치를
뜻하지 않으며, 명시된 과제를 시험할 수 있다는 판정이다.

## 7. 채점과 데모 계약

- 채점 구현은 데모 이전부터 필요한 관측을 준비하되, 데모를 통해 타당성을
  검증한다. 데모를 성공시키려고 합의된 목표를 바꾸는 수단이 아니다.
- 성공·부분 성공·실패·관측 불명의 대응표를 작성한다. 과제에 의미 있는 파손,
  낙하, 오염, 분실, 부품 불완전 체결 등을 선정한다. 무관한 모든 물리 현상을
  구현하겠다는 뜻은 아니다. 중요한 실패를 모델링할 수 없으면 공개하고 task
  타당성을 다시 판단한다.
- 최소 대조군: 무행동, 정상 성공, 목표 인근 미완료, 중요한 금지 행동/파손,
  관측 누락. task에 맞지 않는 대조군은 이유를 기록하고 동등한 검사를 둔다.
- 연속 접촉·유지 시간이 필요한 조건은 전체 구간으로 판정한다. 최종 상태만
  요구하는 과제에는 불필요한 연속 조건을 추가하지 않는다.
- 실행 시 점수와 저장된 궤적의 재채점 결과를 일치시킨다. 재채점에는 필요한
  접촉·관절·위반 이력을 함께 보존한다. 영상만으로 점수를 추정하지 않는다.
- simulator state로 스크립트를 계획하는 것은 허용한다. 물체 순간이동이나
  실행 도중 정답 상태를 주입한 결과를 로봇 데모로 제출하지 않는다.
- 최종 설정의 데모는 깨끗한 reset에서 재실행해 성공을 확인하는 것을 제안한다.
  task의 고정 제출 배치를 먼저 검증하며, 다중 seed 평가는 별도 목적이 있을 때 한다.
- 비디오의 최종 상태와 점수가 일치하고 필요한 후속 유지 구간이 실제로 기록돼야 한다.

## 8. 실패 분류와 수정 범위

| 실패 분류 | 처리 | 자동으로 바꾸면 안 되는 것 |
|---|---|---|
| 근거 부족·잘못된 작업 방식 | 원문 재조사, 후보 보류/제외 | 현실에 없는 절차를 지어내기 |
| 중요성·중복 탈락 | 후보 제외, 다음 유효 후보 검토 | 이름·물체만 바꿔 동일 능력 재포장 |
| 다운로드·환경·일시적 실행 오류 | 원인별 복구 후 해당 단계 재개 | 모든 단계를 처음부터 반복하기 |
| 형상·물리 결함 | 환경 단계 수리, 의존하는 검증을 다시 실행 | 목표 상태에 강제로 고정하기 |
| 도달·파지·제어 실패 | 제어 개선, 필요 시 환경 준비 판정 재검토 | 실행 중 물체 pose를 써서 성공시키기 |
| 채점 오류 | 관측·채점 수정 후 대조군·데모 재검증 | 통과를 위해 실패 조건 삭제 |
| 반복 실패·근본적 실현 불가 | 기록 보존, 예외 보고 후 사람 판단 대기 | 근거 없이 무한 재시도하거나 새 task ID로 우회 |
| Dream 성능 실패 | 실제 결과 기록 후 제출 보고로 진행 가능 | 실패를 이유로 자동 재평가 |
| Dream 상태 불명·계측 오류 | 시도 이력을 유지하고 예외 보고 | 중단을 미사용으로 간주해 자동 재시작 |
| 제출 응답 불명 | PR·미디어·접수 상태 조회 후 재개 | 업로드/PR 중복 생성 |
| 심사 반려 | 원문 피드백 보존, 수정 가능성 분류, 다음 후보 선별에 반영 | 모든 반려를 같은 수정 루프로 처리 |

수정 전에는 실패 원인 가설과 확인 방법을 기록한다. 같은 결과를 반복하면서
새로운 근거가 생기지 않으면 개입을 요청한다.

**기본값 제안, 미확정:** 단계별 수리 계획은 최대 3회, 동일 원인·동일 증거의
실패가 2회 반복되면 예외로 전환한다. 이는 비용 상한이나 공식 대회 규칙이
아니며 초기 파일럿에서 조정할 운영 값이다.

## 9. 결과물 동결·복구·승인

- 모든 실행에 task ID, 후보·명세 버전, 소스·에셋 해시, 실행 환경, seed, 시작/
  종료 시각, 전이 이유, 실제 외부 요청과 응답을 남긴다.
- 검사 결과가 의존하는 입력이 변경되면 결과를 낡은 것으로 표시한다. 형상·
  물리 변경은 환경/데모/채점을, 채점 변경은 대조군/재채점을 다시 검증한다.
- Dream 평가 뒤 의미 있는 변경이 필요하면 그 평가가 새 결과물을 검증했다고
  주장하지 않는다. 변경과 기존 평가의 관계를 보고하고 사람에게 판단을 요청한다.
  새 버전이나 task 이름으로 자동 재평가 제한을 우회하지 않는다.
- 승인 대상은 특정 소스·명세·영상·점수·한계의 묶음이다. 자동 생성된 media ID 등
  제출 메타데이터의 추가를 제외한 의미 변경은 재검토·재승인이 필요하다.
- 최신 중복 검사에서 차단 사유가 생기면 기존 승인만으로 제출하지 않는다.
- 외부 요청 전에 실행 의도를 기록한다. 프로세스가 중단돼도 GPU 작업·Dream
  실행·업로드·PR의 외부 상태를 조회한 뒤 이어간다. 완전한 exactly-once를
  보장한다고 주장하지 않고, 상태 불명일 때 자동 반복을 막는다.
- 승인된 결과를 올렸다는 것과 외부 시스템이 접수했다는 것을 구분한다.
  접수 뒤에는 심사 대기·채택·수정 요청·탈락 등 실제 상태를 확인한다.

## 10. 사용자 보고서

1. 실제 산업 작업의 근거와 자동화할 의미.
2. objective·지시문·장비/도구 setup, 핵심 물리 조작과 조작 자체의 난도 근거.
3. 가장 가까운 기존 과제들과 차이, 비교 범위와 최신 검사 시각.
4. setup 이미지, 전체 데모 영상, 최종 상태, full-score 근거.
5. 채점 조건, 대조군 결과, 중요한 파손·위반·관측 유효성.
6. Dream 실제 점수·영상·종료 이유와 평가 실행 이력.
7. fidelity의 근사, 빠진 기능, 미해결 한계와 자체 심사 결과.
8. 소스·에셋·환경·라이선스의 재현 가능 자료와 제출 예정 버전.
9. 승인/수정 요청/보류 판단에 필요한 항목과 예외 사항.

보고·승인 수단은 아직 정하지 않는다. 특정 메신저로 보내는 기능은 별도
설계·권한 범위가 필요하며 이번 문서 작성으로 메시지 발송을 허용하지 않는다.

## 11. MVP 자체의 완료 조건

- 실제 산업 근거가 있는 후보 여러 개의 검토와 선정/탈락 이유가 남는다.
- 한 태스크를 환경 준비 판정 → 데모/채점 검증 → Dream 최종 평가 → 최신 중복
  검사 → 사용자 승인 → 제출 접수 확인까지 수행할 수 있다.
- 실패한 Dream 결과도 재평가 없이 보고할 수 있다.
- 중단/재개, 누락된 관측, 실패 대조군, 제출 직전 중복 발견, 승인 대상 변경,
  외부 응답 불명 등에서 잘못된 통과·중복 실행을 막는다.
- 파일럿에서 단계별 소요 시간, 후반 환경 재작업, 사람 개입 횟수·이유,
  뒤늦게 발견한 품질 문제, 실제 심사 피드백을 기록한다.
- 한 번의 성공으로 매일 1개 또는 채택률을 보장하지 않는다. 추가 운영에서
  관찰하고, 하루 목표를 맞추려고 검증을 생략하지 않는다.

## 12. 후속 확정 사항

산업 자료의 구체적인 목록과 조사 범위, 단계별 반복 실패 기준, 실제 설치
런타임과 도구 버전, task별 물리 허용 오차·재현 횟수는 후속 결정한다.
카탈로그 수집·보고/승인·에이전트 실행의 기술 선택과 계약은 상세 기술 문서의
검토 제안이며 아직 설치·동작 검증 또는 최종 승인을 의미하지 않는다.
구현 순서·검증 계획과 미착수 태스크 목록은 [구현 계획](../../tasks/plan.md)에
정리했다. 아직 코드·배포 설정을 만들거나 실제 구현을 시작하지 않는다.
