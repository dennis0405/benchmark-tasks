# MVP 구현 순서와 검증 계획

상태: 2026-11-13의 최초 구현 계획. 2026-11-14 구현·검증 상태는 [구현 현황](implementation-status.md)을 따른다.
구현 체크리스트는 [todo.md](todo.md), 사전 준비와 사용자 결정은
[Brev 준비 문서](../docs/design/brev-readiness.md)에 기록한다.
상위 기준은 [제작 의도](../docs/intent/robocurve-automation.md)와
[전체 기술 구성](../docs/design/technical-architecture.md)이다.

## 1. 구현 전략

최초 목표는 한 산업 태스크의 전체 경로를 신뢰할 수 있게 완주하는 것이다.
처음부터 일일 예약 실행·대규모 병렬 제작·여러 embodiment·새 연성 solver를
만들지 않는다. 여러 후보를 비교하되 제작 중인 후보는 하나로 제한한다.

- 첫 GPU 점검은 기존의 작은 YAM 예제다. 이는 런타임 진단이며 산업 후보나 제출 데모가 아니다.
- 외부 접수와 유료 평가는 fake transport로 먼저 연결한다. 실패 복구가 된 뒤 실제 한 번을 실행한다.
- 산업 후보의 환경 준비가 끝나기 전에 해당 후보의 전체 데모 개발을 시작하지 않는다.
- 실험과 생성 에이전트는 유료 평가·제출 자격증명을 상속하지 않는다.
- 단계별 checkpoint는 자동 검사다. 매 단계 사람 승인을 추가하지 않는다.
  구현 시작 여부의 현재 검토, 예외 개입, 최종 결과물의 제출 승인을 구분한다.
- 한 작업이 5개 안팎의 파일이나 한 집중 작업 세션을 넘으면 구현 전에 더 나눈다.
  아래 파일 위치는 제안이며 아직 코드·설정 파일은 없다.

## 2. 의존관계와 순서

```text
P0. 접속·인증·작은 YAM 런타임 확인
 ↓
P1. 기록/복구 기반 → 에이전트 어댑터 → 가짜 결과로 전체 상태 전이
 ↓
P2. 제출/산업 자료 수집 → 중복 검사 → 후보 다수 비교·하나 선정
 ↓
P3. TaskContract → 에셋·환경 → 물리/관측 준비 판정
 ↓
P4. 채점 로직/대조군 → 로봇 데모 → 깨끗한 export본 재현
 ↓
P5. Dream 모의 실행 → 보고·승인 → 제출 모의 실행·복구
 ↓
P6. 최종 점검/동결 → 실제 Dream 1회 → 최신 중복/보고 → 사용자 승인
 ↓
P7. 실제 업로드·PR·접수 확인 → 보존/복구·운영 평가
```

P5의 fake 평가·제출 시험은 P1 이후 더 일찍 수행할 수 있다. 실제 Dream은
P2~P5의 필수 검증과 새 환경 재현을 모두 통과한 뒤에만 허용한다.
수집과 CPU 분석이 GPU 작업의 자원을 잠식하지 않게 한다.

| 구간 | 작업 ID | 사용자에게 보여줄 산출물 | 다음 단계 통과 조건 |
|---|---|---|---|
| P0 준비·위험 확인 | T01~T03 | ReadinessReport, YAM 짧은 영상·관측, EnvironmentLock | 실제 CLI/컨테이너/GPU/렌더·관측 호환 확인. Dream 요청·업로드 없음 |
| P1 복구 가능한 최소 흐름 | T04~T06 | fake run의 상태 이력·보고서·중단/재개 결과 | 잘못된 통과·중복 시작·가짜 승인을 차단 |
| P2 근거·신규성·후보 | T07~T10 | 출처 카탈로그, 수집 커버리지, 후보 비교·중복 보고 | 필요한 범위의 수집 완료, 산업 근거·신규성이 있는 후보 하나 |
| P3 환경 준비 | T11~T13 | TaskContract, 에셋 manifest, 물리·관측 검사 | 핵심 장비/상호작용과 성공·실패 관측이 유효 |
| P4 데모·채점·이식 | T14~T16 | full-score 영상, 실패 대조군, trace 재채점, 재현 결과 | 실제 로봇 성공·오채점 방지·export본 재현 |
| P5 외부 실행 방어 | T17~T19 | mock 요청 이력, 검토 보고서, 승인/제출 복구 결과 | 평가 재시작·승인 우회·중복 업로드/PR 방지 |
| P6 실제 평가·검토 | T20~T21 | 고정 입력, Dream 실제 결과, 최신 중복·최종 보고 | 실제 결과가 유효하고 미해결 핵심 문제 없음. 제출은 승인 대기 |
| P7 승인 후 제출·운영 | T22~T23 | PR·접수 상태, 복구 증거, 파일럿 회고 | 승인 자료와 외부 접수가 연결되고 기록 복구 가능 |

## 3. 단계별 검증 방법

### P0: 접근 가능과 실행 가능을 구분

로컬 Brev CLI 로그인·SSH·VS Code를 확인한 뒤 원격 host/container 경계를
기록한다. GPU 모델·driver와 선택한 Isaac Sim 버전의 요구 사항을 대조하고
컨테이너 안에서 실제 렌더·YAM reset·짧은 제어·카메라·관측을 확인한다.
`nvidia-smi`나 CUDA tensor 시험만으로 Isaac Sim 검증을 대신하지 않는다.

첫 체크포인트가 실패하면 버전/driver/컨테이너 문제를 먼저 해결한다.
전체 산업 자료 수집기·에이전트 군집을 만든 뒤 런타임 불일치를 발견하지 않게 한다.
기존 서버·과자봉지 branch·실행 중 작업은 이 계획의 변경 대상이 아니다.

### P1: fake 자료로 전체 흐름과 중단 복구부터

RunRecord·외부 요청 journal·상태 전이·입력 해시·단계 소유권을 먼저 만든다.
유효한 fake 산출물로 선택→환경→데모→평가→승인 대기까지 연결한다.
유료/제출 경로는 transport가 실제 네트워크 요청을 못 하게 대체한다.

프로세스 중단, 같은 run 동시 시작, 오래된 보고서, 누락된 증거, 에이전트가
쓴 승인 값을 주입해 차단되는지 확인한다. SQLite WAL을 무시한 파일 복사가
아닌 일관된 backup 경로를 검증한다. 복구 불명인 외부 요청은 `unknown`으로
유지하며 시도하지 않은 것으로 초기화하지 않는다.

### P2: 수집 정확성과 중복 검사의 놓침 확인

GitHub 전수 페이지네이션·revision과 board 대응을 먼저 검증한다.
공개 산업 자료·에셋은 작업 실재성·자동화 가치·조작 난도·라이선스를 연결한다.
관측된 사실과 추정, 현재 제출본과 과거 revision을 나눠 보존한다.

기존 중복/변형 사례와 실제로 다른 능력의 쌍으로 회귀 자료를 만든다.
검색 상위 결과에 없던 중복, 전수 signature의 누락, 다른 카테고리·우리 팀 사례도
시험한다. 개발에 사용한 쌍과 별도 보류 검증 쌍을 구분한다.
카탈로그 완성·의미 판정·검색 성능을 하나의 정확도 숫자로 합치지 않는다.
알려진 차단 사례를 놓치면 후보 제작을 막는다. 미지 중복 0건을 보장하지 않는다.

### P3: 환경과 관측을 먼저 완성

후보의 목표·근사·성공·부분 점수·파손·금지 행동·측정 계획을 계약으로 고정한다.
사용할 산업 장비 한 종류의 형상·collision·관절·단위·질량을 검증하고,
reset/낙하/파지/해제/삽입/잠금 등 필요한 구성요소 시험을 수행한다.

센서 누락·오래된 pose·잘못된 좌표계·순간 위반 누락을 시험한다.
구성요소 fixture의 직접 누름이나 초기 배치는 허용하되 로봇 데모와 구별한다.
핵심 물리·계측이 불안정하면 데모 단계로 보내지 않는다.

### P4: 채점과 로봇 성공을 서로 대조

먼저 계약에 따른 채점 로직·경계·실패 누적을 검증한다. 이후 full-score 로봇
데모와 무행동·근접 미완료·관련 파손/금지 행동·관측 누락 대조군을 실행한다.
raw trace 재채점과 실행 중 점수가 일치해야 한다.

초기 제안은 최종 설정·고정 제출 배치에서 깨끗한 reset **3회 모두 full score**다.
아직 사용자 확정값은 아니며 task별 수치 오차는 별도 근거로 정한다.
이 검사는 일반화 성공률 또는 현실 물성 검증을 뜻하지 않는다.

서버의 숨은 파일이나 개발 디렉터리가 없는 새 컨테이너에서 export본으로
데모·채점·카메라를 재현한다. 코드/물리 변경은 의존 결과를 무효화한다.

### P5: 유료·외부 요청을 소비하지 않는 실패 시험

Dream 어댑터의 constructor·warmup·dry-run·retry·세션 재생성을 실제 설치
소스에서 추적하고 fake transport로 요청 수와 attempt 상태를 확인한다.
평가 예약 직후 중단, 응답 일부 수신 후 단절, 비용/세션 상태 불명을 시험한다.
SDK import/생성 자체가 요청을 보낼 수 있으므로 실제 키 없는 격리 시험을 먼저 한다.

사용자가 본 ReleaseManifest와 다른 소스·영상·scorer를 넣으면 승인을
거부하는지 확인한다. 모의 업로드/PR 응답 유실 시 조회·대기 상태로 복구하고
자동 재생성이 없는지 시험한다. 연습용 PR이나 테스트 미디어를 실제 대회에
보내지 않는다. 배포 시 실제 접수 경로 검증은 P7에서만 수행한다.

### P6~P7: 실제 한 번의 파일럿

입력·runtime·데모·채점·영상·export 검증을 고정하고 실제 Dream 한 평가를
실행한다. 결과가 낮아도 유효한 성능 결과라면 그대로 보고한다. 계측/실행이
불명확하면 예외로 보내며 자동 재평가하지 않는다.

최신 accepted·pending·관련 보호 revision·자기 팀 제출·벤치마크를 다시
비교하고 결과·한계·라이선스·제출 예정 파일을 보고한다. 사용자의 구체적인
승인을 받은 뒤 승인 버전으로 업로드·commit·push·PR을 수행한다.
승인 대기 후 변경/새 중복 여부도 실행 직전에 확인한다.

외부 접수 확인까지를 파일럿의 완료로 본다. 대회 채택 여부는 별도 후속 상태다.
실행 기록을 새 작업 공간으로 복구해 source/hash/journal·Dream 이력·승인·
미디어/PR 연결이 유지되는지 확인한다. 이를 위해 원래 VM을 삭제하지 않는다.

## 4. 실패 처리와 자동 수리의 한계

| 문제 | 자동으로 할 일 | 멈추는 조건 |
|---|---|---|
| 수집 일시 오류 | 오류별 backoff·기존 snapshot 보존 | 필수 자료 범위를 완성할 수 없음 |
| 후보 중복·근거 부족 | 제작 전 다른 유효 후보 선정 | 후보 전부 탈락, 근거/판정 불명 |
| 에셋·물리·제어·채점 오류 | 원인 가설과 수정 범위를 정해 해당 단계만 수리 | 반복 실패 기준 도달, 핵심 목표 약화가 필요 |
| 관측·영상·trace 누락 | 기록/계측 수정, 필요한 demo 재실행 | Dream에서 발생하면 자동 재평가 없이 예외 |
| Dream 성능 실패 | 실제 결과 보존·보고 | 실행 무효·상태 불명 또는 누적 사용액 불명 |
| 승인 뒤 내용 변경 | 재검증·새 검토 대상 생성 | 새 승인 전 제출 금지 |
| 업로드/PR 응답 유실 | 외부 상태와 journal 대조 | 복구할 공식 경로가 없거나 상태 불명 |

반복 수리는 기존 제안인 단계별 최대 3개 수리 계획, 같은 원인·같은 증거
2회 반복 시 예외 전환을 유지하되 **미확정**이다. 단순 HTTP transport 재시도,
새 수정 실험, Dream 평가 실행을 같은 횟수로 세지 않는다.
선정 후 근본적으로 실현 불가한 경우 자동으로 목표를 바꾸거나 다른 후보를
몰래 제작하지 않고 결과를 보존해 예외 보고한다.

## 5. 파일럿 이후에만 추가할 것

단계별 시간·수리 원인·사람 개입·외부 심사 피드백을 보고 보완한다.
전체 흐름이 안정된 뒤 backlog에서 한 후보를 순차 제작하는 일일 운영을
붙인다. 하루 1개는 운영 목표이며 일일 제출을 강제로 채우는 조건이 아니다.
지정한 기존 GPU instance start/stop과 로컬 CLI·전용 skill은 사용자 확정에 따라
첫 MVP에 포함한다. 예약 실행·GPU 자동 신규 생성·공개 대시보드·다중 제작 worker는
별도 후속 범위다. 상세 계약은 [생명주기 설계](../docs/design/cli-skill-and-lifecycle.md)다.

추가 작업 T24(CLI·생명주기)는 T04 뒤/T06 전에, T25(fork checkpoint)는
T16 뒤/최종 평가 전에, T26(skill)은 CLI·승인·제출 모의 검증 뒤에 배치한다.
T21의 실제 평가 결과도 fork 작업 브랜치에 보존한 뒤 stop해 검토한다.
승인/제출은 로컬에서 진행하며 수정 요청 때에만 start·resume한다.

## 6. 구현 전 검토 상태

단계와 검증 순서는 제안이며 아직 사용자의 구현 시작 지시가 없다.
로그인/키 발급, 파일럿 조사 범위, 저장·복구 목적지, 제출 계정·fork 확인은
[준비 문서](../docs/design/brev-readiness.md)를 따른다.
기술 상세의 검토와 실제 결과물의 제출 승인은 별개다.
